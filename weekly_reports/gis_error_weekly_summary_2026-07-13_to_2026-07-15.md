# GIS Error-aware Agent 本周工作总结

时间范围：2026 年 7 月 13 日至 2026 年 7 月 15 日

汇报重点：本周核心工作是将“具体 GIS 错误案例”抽象为“可泛化的 GIS 错误感知规则”，并在此基础上搭建 Error-aware 对比实验框架。


# 一、本周核心结论

本周最重要的进展，不是继续罗列更多错误案例，而是完成了从“案例级规则”到“泛化错误感知规则”的转变。

这个转变是 Error-aware Agent 后续能够提升 GIS 任务正确率的关键。原因在于：如果规则只对应某个具体案例，agent 容易变成“对着答案做题”；只有把规则抽象到 GIS 语义不变量层面，agent 才能在新任务、新数据和新错误表述下进行迁移判断。

本周形成的核心方法是：

具体错误案例

→ 抽象出被破坏的 GIS 语义不变量

→ 写成高召回错误假设探针

→ 用分类指南做边界判定

→ 用案例知识库补充类比证据和修复回馈

→ 插入多 Agent 系统形成 Error-aware 修复闭环


# 二、规则泛化的动机

前期针对具体案例写出的规则存在一个明显问题：它们能够解释已有错误，但不一定能覆盖未来 benchmark 中的新错误形态。

例如，如果规则只写成“bounds 是否交换”“字段是否为空”“颜色是否错误”，agent 很可能只会匹配表面现象。一旦任务换了数据格式、换了表达方式，或者错误没有出现同样的日志和字段名，规则就可能失效。

因此，本周对规则卡做了重新定位：

1. **规则卡不是最终分类器**

   它只负责生成候选错误类别，不能因为未命中规则就判定任务正确。

2. **规则卡不是案例库**

   它不记录某个样本的答案，也不写具体修复代码。

3. **规则卡是 GIS 语义不变量探针**

   它关注的是任务结果是否破坏了某类 GIS 语义契约，例如空间参考、数据表示、空间关系、分析范围或地图表达。

这使得规则卡能够承担 Error-aware 系统中的第一层功能：先把可疑错误召回出来，再交给分类指南和案例知识库进一步判断与修复。


# 三、规则泛化的具体过程

本周规则泛化主要经历了四步。

**第一步：从表面错误现象上移到 GIS 不变量**

原先容易写成“看到某个函数、字段、日志就归类”。现在改为先判断错误是否破坏 GIS 任务中必须保持的语义不变量。

例如：

- A1 不再只看经纬度 bounds 是否交换，而是关注“空间维度身份”是否被错置。
- C3 不再只看是否构建节点-边图，而是关注“可达性和连通关系模型”是否被错误替代。
- E2 不再只看颜色是否不好看，而是关注“视觉变量是否正确表达类别、顺序、强度或数量语义”。

**第二步：从 evidence questions 改为 diagnostic axes**

为了避免规则过窄，规则卡不再列出很具体的检查问题，而是采用统一的语义诊断轴：

- semantic_precondition：任务中必须成立的 GIS 语义前提是什么；
- process_contract：工作流是否在读取、转换、分析和输出过程中保持该语义；
- outcome_consistency：最终结果是否仍然符合任务预期的空间语义；
- neighbor_disambiguation：如何与相邻类别区分。

这一步的作用，是让 agent 不只根据关键词匹配，而是沿着“前提—过程—结果—边界”的链条进行诊断。

**第三步：加入概念解释，降低抽象规则的误判风险**

只写抽象规则会导致 agent 不知道“空间维度身份”“空间支持”“视觉编码语义”等概念具体指什么。因此规则卡中加入了 concept glossary 和 concept_definition。

这些解释允许使用具体 GIS 概念，例如 lon/lat、x/y、EPSG、NoData、Shapefile 组件、路网节点边、颜色映射等。这样做不是回到案例模板，而是帮助 agent 理解抽象概念。

**第四步：明确 non-match policy**

每张规则卡都明确写入：未命中规则不代表结果正确，只代表当前证据不足以确认该类错误。

这个设计非常重要。它避免 agent 把“没有匹配到规则”误解成“任务没有错误”，从而降低隐形错误漏检风险。

# 五、规则卡与案例知识库的分工

规则卡和案例知识库不是同一种东西。本周已经把二者边界拆开。

**规则卡负责初筛**

规则卡回答的是：当前失败结果可能违反了哪类 GIS 语义不变量？

它的目标是高召回，不追求一步定准。规则卡不会直接给修复代码，也不会因为未命中就判定正确。

**案例知识库负责修复回馈**

案例知识库采用双层结构：

- `retrieval_text`：短文本，用于 RAG 召回相似 verified 案例；
- `repair_playbook`：详细修复回馈，用于说明错误像什么、根因在哪里、该改什么、不该怎么改、如何验证修复。

这种分工可以防止两个问题：

1. 规则卡被案例细节污染，失去泛化能力。

2. 案例库只做相似检索，却不能指导 agent 真正修复。


# 六、Error-aware 模块为什么可能提升正确率

普通 self-debug 主要依赖 traceback、运行日志和模型自身经验。它对于显式代码错误有帮助，但对 GIS 隐形错误不够稳定，例如 CRS 错位、NoData 误统计、空间支持错配、地图表达缺失等。

Error-aware 模块的增益点在于：

1. 它先从 GIS 语义不变量角度发现可疑错误，而不是只看代码是否报错。

2. 它能把 evaluator 的失败现象转化为候选错误机制。

3. 它能用分类指南排除相邻类别，减少错误归因混乱。

4. 它能通过案例知识库给出结构化修复回馈，而不是只让模型自由猜修复方式。

因此，Error-aware 的核心不是“多检索几个案例”，而是把 GIS 专业错误知识嵌入到失败诊断和修复决策链条中。


# 七、对比实验框架

在上述规则泛化和知识库建设基础上，本周搭建了任务四对比实验框架，用于后续验证 Error-aware 模块是否真正提升任务正确率。

实验保留三组系统：

1. **baseline multi-agent**

   普通多 Agent GIS 执行系统，只执行任务，不使用修复闭环。

2. **self-debug multi-agent**

   在普通多 Agent 系统上加入 traceback、日志和 evaluator 可见报告驱动的普通自调试。

3. **error-aware multi-agent**

   在同一多 Agent 宿主系统中插入 Error-aware 插件，插件读取规则卡、分类指南和案例知识库，生成 GIS 错误感知修复建议。

# 九、汇报时建议强调的结论

本周最核心的工作，是把具体 GIS 错误案例抽象为可泛化的规则卡，使 Error-aware Agent 不再依赖案例表面匹配，而是能够从 GIS 语义不变量角度诊断错误。

规则泛化是 Error-aware 模块可能提升正确率的关键；案例知识库则负责在规则初筛之后提供类比证据和修复回馈。

任务四框架的作用，是在后续正式 benchmark 和 evaluator 接入后，验证这套“规则泛化 + 案例修复回馈”的 Error-aware 模块，是否能相对普通 self-debug 多 Agent 系统带来实际正确率提升。
